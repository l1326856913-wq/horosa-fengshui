# Horosa FengShui AR

实时风水堪舆系统：手机摄像头多帧空间序列 + 罗盘 / 卫星地图拉线定向，后端 `mingyu-core` 引擎完成玄空飞星 + 八宅明镜排盘，前端调用多模态大模型结合多角度实景进行整体空间堪舆分析。iOS PWA 风格，暗黑金 AR HUD。

## 目录结构（实际）

```
horosa-fengshui/
├── api/
│   └── index.js          # Vercel Serverless：/api/health、/api/horosa（排盘）、/api/map（高德静态图）、/api/ai（大模型流式代理）
├── public/
│   ├── index.html        # iOS PWA 前端：摄像头 AR、EMA 罗盘滤波、Leaflet 卫星图拉线定向、流式对话
│   ├── manifest.json     # PWA 配置
│   └── icon-*.png        # PWA 图标
├── dev-server.mjs        # 本地开发服务器（模拟 Vercel 环境）
├── test-engine.mjs       # mingyu-core 排盘引擎验证脚本
├── package.json
└── vercel.json           # Vercel 部署配置
```

## 关键设计（防止幻觉与误差）

1. **八方位定向采集替代单帧**：先罗盘锁定基准，再引导依次对准 8 个罗盘方位（正北/东北/正东/东南/正南/西南/正西/西北，±12° 内稳定 0.8 秒自动拍摄，可跳过），每帧按"方位→九宫→飞星"与排盘映射解读；系统指令含八方位-九宫映射铁律（禁止把不同帧误判为不同房间）。
2. **理气与断语分离**：所有坐向、飞星、命卦均由 `mingyu-core` 确定性引擎计算，AI 只做解读，System Instruction 明确禁止 AI 重算或改写排盘数字；回复中的山向/命卦表述经前端机器交叉核对，不一致即亮黄牌。
3. **磁偏角自动修正**：手机罗盘输出磁北方位，后端按 GPS 坐标用 WMM（`geomagnetism`）计算当地磁偏角换算真北（北京约 -7.5°，不修正足以错判一整山）。
4. **双定向模式**：卫星地图拉线定向直接得到真北方位角（无需磁偏角）；罗盘模式走磁偏角修正链路。
5. **测量误差显式建模**：罗盘 ±3°；地图拉线按线长动态估算点选误差（下限 ±1.5°，拉线过短会强警示），读数靠近二十四山分界或下卦/兼向边界时，引擎返回候选山向与复测警示而非强行下断。
6. **引擎业务校验**：缺建造年、缺 GPS、度数越界等情况返回可读的 400 提示，不伪造数据。
7. **两步站位指引与室内外口径匹配**：先选勘测环境（室外/室内），再选该环境下的站位方式（室外·门外定向 / 室内·立极环拍 / 室内·区域复查）；环境与站位注入 prompt，AI 按对应口径解读。
8. **补拍闭环**：AI 判断画面不足时输出【重拍请求】，前端出现补拍按钮；补拍序列以【第N轮补拍】追加进对话，AI 带前轮记忆整合分析（单次勘测最多 3 轮）。
9. **勘测记忆**：每次分析结论自动留存（时间/方式/坐向/运/命卦/摘要，保留最近 2 条），下次勘测自动注入，冲突以本轮实测为准；📜 按钮可查看与清除。

## 核心接口

- `POST /api/horosa`：`{ heading, northReference: 'magnetic'|'true', lat?, lng?, year(建造年), birthYear?, gender?, uncertainty? }` → 玄空 + 八宅完整排盘与结构化证据提示词
- `POST /api/ai`：`{ provider: 'gemini'|'deepseek'|'glm', apiKey, payload }` → 流式转发大模型 SSE（规避浏览器 CORS）
- `POST /api/map`：`{ lat, lng, gaode_key }` → 高德静态外局图 base64
- `GET /api/health`：健康检查

## 第三阶段：知识层可追溯性加固（2026-10-04）

第二阶段修完运界后，复检发现**紫白流年盘仍按公历年干支**——而干支年本身以立春换界（实测 `SixtyCycleYear.fromYear(2024)` 返回甲辰年而非甲子年）。结果是同一张盘出现两套时间标准：运界已回退到 2023，流年却仍取 2024。本阶段连同三项残留问题一并修复。

| 问题 | 根因 | 修复 |
|---|---|---|
| **流年盘未按立春换年** | `resolveYearFlyingStar(year)` 只收年份，内部用公历年号取以立春为界的干支年，每年 1/1~立春期间流年星错一星 | 新增 `resolveFlowYearByLichun()`；补齐流年参照月/日即走引擎节气年路径（该路径本身正确）。实测 `2026-01-15` 由一白修正为二黑（2025 干支年） |
| **星性宜忌表无出处** | `STAR_RULES` 九条宜忌全表硬编码在前端，无一条标注流派依据；`remindersPanel` 却标注「确定性规则，非AI生成」，实为本地常量 | 九条全部补 `source`（引《协纪辨方书》或明示「各家共识」）与 `wuxing`；标注改为诚实表述「本地通行星性口径归纳表，非引擎输出」，并声明流派差异；UI 增设〔依据〕悬停提示 |
| **重拍按钮可能误触发** | `reply.includes('【重拍')` 纯字符串匹配，而兜底路径下 `fullReply` 是**思考流**，其中出现「重拍」二字即误触发 | 新增统一门控 `isFormalReply(reply)`，以 `__meta.formal` 判定；首轮、补拍轮、以及两处记忆写入全部改用该门控 |
| **城门诀推导被丢弃** | 前端只渲染 `castleGate.summary` 一句结论，引擎给出的完整推导链全部丢弃，用户无法区分「此盘无城门」是算错还是格局如此 | 展开 `candidates`：逐条显示正/副城门、运星、顺逆飞向、飞临星、判定结论；无城门时明示「属格局本身如此，非排盘错误」 |

### 顺带修掉的一处安全隐患

复检星性表转义时发现：排盘面板存在**引擎字段未转义**直接插入 `innerHTML` 的情况（`p.name`、`p.direction`、`p.shanXiangRelation`、`x.period.label`、`b.mingGua`、四吉位 `d.direction`/`d.label` 等）。虽当前引擎输出均为纯文本、未构成实际风险，但一旦上游返回含尖括号的字符串即会破坏 DOM。现已全部收敛到 `escHtml(String(...))`。

### 新增设置项

「**流年参照月/日**」（可选）：与建造月/日同理，流年紫白按立春换年。若所填为当年且在 1/1~立春之间，填「今天」即可对齐；不填则按公历年判定并在罗盘面板给出边界告警。

## 第四阶段：算法层防幻觉（2026-10-04）

### 问题定性

前三阶段修的是"引擎算得对不对"。但项目还有另一条独立的失效路径：**引擎算对了，AI 复述时编错**。

典型场景：引擎排出九运丙山壬向，AI 却写"此局八运"。用户看引擎面板是九运、看 AI 解读是八运，无从判断该信哪个——这比算错更危险，因为它是**权威地错**。

本阶段的处理原则：**AI 不得参与算法**。它只是把引擎结论翻译成白话，并描述图片里看得见的东西。

### 三道防线

**第一道：提示词隔离（降低动机）**

核心发现——原提示词里有一条自相矛盾的条款：

> K. 回复结构（引擎优先）：回复须以"引擎排盘要点"开篇（引用系统给定的坐向、运、局型、命卦等关键结论……）

这条指令**要求 AI 复述算法数字**，正是幻觉的直接诱因。已重写为"引导用户查看上方引擎面板"，全文不再要求 AI 输出任何术数数字。

新增铁律（现共 A–O 条）：

| 条款 | 内容 |
|---|---|
| A | 你是**翻译器**不是排盘引擎；禁止复述、改写、换算任何引擎数字 |
| B | **无结论即无话可说**：引擎没排的项目不许提、不许猜（城门/四吉四凶/命卦/流年四类禁区逐一列明） |
| C | **数字纪律**：默认正文零术数数字；用户直接问时才可照抄引擎面板原值，且禁止二次运算 |
| M | 开篇只引导看面板，不复述数字；全文只做"描述形煞→说明影响→给建议" |
| O | 白话表达：仅在用户主动询问时才解释术语 |

另在**排盘数据紧邻处**插入【只读声明】。位置很关键：铁律在消息开头、数据在中间，模型注意力随距离衰减，把约束重复在数据旁边能显著降低"看到数字就顺手复算"的倾向。补拍轮同样加了【只读提醒】。

**第二道：引擎事实表（冻结唯一事实源）**

`buildEngineFacts(hData)` 在引擎返回后**立即**冻结 15 类可断言结论：

```js
window.__engineFacts = buildEngineFacts(hData);
```

此后 AI 文本只能被它比对，不能反向修改它。事实表采用**封闭白名单**——只有引擎实际产出的字段才进入，引擎没产出的字段不存在核对基准（这也意味着"AI 在无引擎依据处自造结论"需由提示词层第一道防线兜住）。

**第三道：逐项机器核对 + 幻觉对照表**

`verifyAIReply(reply, facts)` 对 AI 回复做 15 类字段的逐项比对，覆盖引擎一张完整九宫盘的全部 27 个飞星数字（9 宫 × 运星/山星/向星）。

检出后不静默丢弃、也不静默相信，而是在 AI 回复下方渲染三列对照表：

| 字段 | AI 表述（错误） | 引擎结论（正确） |
|---|---|---|
| 巽宫山星 | 七 | 6（六白） |

核对逻辑写在 `callAIStream()` 内部，因此**首轮、补拍轮、追问轮三条路径自动全覆盖**；兜底路径（GLM 只输出思考流）自动跳过，避免探索性表述大量误报。

### 验证

```bash
node verify-anti-hallucination.mjs   # 49 项：14 类幻觉注入攻击 + 零误报 + 提示词条款断言
```

六关设计：

1. 事实表完整性
2. 正确回复零误报
3. **14 类幻觉注入攻击**（篡改坐向/命卦/宅卦/运数/局型/卦型/九宫山星/向星/运星/生克/城门/四吉四凶/命宅关系）——全部抓出
4. 封闭白名单：事实表不含无引擎依据的字段
5. 性能与健壮性：20 倍长文本不超时、空输入安全
6. **提示词层纪律断言**：把铁律条款本身做成测试，防止后续重构不小心删掉或改软

第 6 关的存在意义：机器核对只能抓"AI 说错"，抓不住"AI 从没被禁止"。提示词是唯一能降低幻觉动机的地方，因此必须给它上回归测试。

### 已知局限（如实说明）

`verifyAIReply()` 基于正则匹配，能覆盖常见表述，但**不可能穷举所有自然语言改写**。若 AI 用"这个位置在当前运下最旺"这类纯定性表述，事实表无从比对——这正是第一道防线（提示词禁止输出数字）存在的原因。两道防线互补，不是一道能解决的问题。

## 第五阶段：核对层去 AI 化（2026-10-04）

### 起因：一次自我审查

第四阶段的核对规则全部由 AI 编写。审查发现其中**三处是用 AI 自己的玄空知识去覆盖引擎输出**，方向与项目要求相反：

| 原实现 | 问题 |
|---|---|
| `_GONG_ALIAS` 九宫→方位映射表 | 引擎已在 `palaces[].direction` 给出权威方位，前端又建一套。两套并存时若不一致，会出现「AI 说对了却被判幻觉」 |
| `guaTypes=['正卦','下卦','上卦','全卦']`、`forms=[旺山旺向,上山下水,双星到坐,双星到向]` | 凭玄空记忆手写。**实测穷举 720 个半度 × 4 个建造年 = 2880 个盘面，引擎 `guaType` 只产出「下卦」一种**——清单里另三个值引擎根本不产生，等于用虚构值域校验权威输出 |
| `castleGate` 用 `/可用\|合/.test(status)` 猜可用性 | 把引擎已用布尔回答的问题重新实现为中文文本匹配。且实测 `hasUsableGate=true` 时两候选 status 有 3 种合法组合，按单个候选判定本身就不成立 |

### 修改原则

**只信引擎，不信前端清单。** 所有真值改为现取自引擎字段，前端不再维护任何术数枚举：

- 九宫键：`pl.name` 字符串解析 → **`pl.gong`**（引擎语义主键）
- 九宫方位：`_GONG_ALIAS` 硬编码表 → **`pl.direction`**
- 九宫匹配字符集：常量表 → **运行时从本次 `gongChar` + `direction` 收集**
- 山名：固化二十四山清单 → **运行时从 `sitMountain`/`facingMountain`/城门山名收集**
- 卦型/局型：枚举清单比对 → **直接全等裁决**（引擎给什么就比什么，不预设值域）
- 生克关系：手写词表 → **本次 palaces 去重生成**
- 城门可用性：`status` 字符串猜测 → **`castleGate.hasUsableGate` 布尔字段**
- 四吉四凶：前端「吉/凶」字面量 → **引擎 `d.luck`**，并展示 `d.label` 依据

### 同时暴露并修复的两个隐性缺陷

改写过程中发现两处**静默失效**——不报错，只是防线悄悄不起作用：

1. **捕获组索引错位**：方位部分从捕获组改为非捕获组 `(?:...)` 后，数字仍在 `m[2]`，取到 `undefined` → 18 条九宫攻击全部漏检。改为具名捕获组 `(?<alt>…)(?<n>…)`，从根本上消除索引歧义。
2. **字符集未包括号**：`collectMountainChars` 返回 `子午巽坤`，拼成 `坐子午巽坤{1,2}向…`，量词作用于整串，匹配恒为空。改为返回 `[子午巽坤]`。

两者都是「看起来在跑、实际零效果」——**这类缺陷任何单次正向测试都发现不了**。

### 测试重写：从「自己判卷」到「引擎说了算」

v1 的根本缺陷：攻击样本由 AI 手写、核对规则也由 AI 手写，等于自己给自己判卷。49/49 全绿只证明「AI 的规则与 AI 的样本自洽」。

v2 的改变：

- **攻击样本由引擎真值机械变换生成**（改一个数字即为错），不再杜撰措辞
- **新增非对称测试（第 3 关）**：喂引擎真值，验证核对层不得报错。AI 说对了却被拦，说明规则本身错了——这是 v1 完全缺失的方向
- **新增规则来源审计（第 4 关）**：断言核对层代码中不含任何术数硬编码值域，防止日后改回旧写法
- **新增无依据放弃核对（第 5 关）**：引擎为空时必须放行，禁止用前端默认值硬比。宁可漏检，不可误拦


## 已知风险与维护清单

**数据层**
- `geomagnetism` 内置 WMM-2025 地磁模型，**有效期至 2029 年 11 月**。过期后库会静默用旧模型外推（每年约漂移 0.1°），届时需升级该依赖或换用官方 WMM 新版。

**部署层**
- `vercel.json` 采用 `builds + routes` 显式配置（api 走 `@vercel/node`，public 走静态）。未设 `maxDuration`（Hobby 默认 10s 仅约束非流式等待，流式响应不受影响）；若函数被提前截断可自行加回。
- API 无鉴权无限流，公开部署后任何人都可消耗你的函数配额。商用前建议加 IP 限流（如 Vercel Firewall / Upstash Rate Limit）。
- 高德 Key 建议在高德控制台绑定域名白名单，防止盗用。

**隐私与合规**
- 应会上传 GPS 坐标、罗盘读数、室内照片至所选大模型服务商（用户自己的 Key）。需在产品页明示并取得用户同意；商用前补充隐私政策与免责声明。
- AI 密钥存于浏览器 localStorage，存在 XSS 窃取面；面向公众商用时应改为服务端密钥 + 用户体系。

**测量操作层（准确性的最大变量）**
- 手机罗盘受金属、磁铁、手机壳、车内环境影响极大，测量前务必画"8"字校准并远离干扰源（App 已内置提示）。
- 读数落在二十四山分界或下卦/兼向边界（±4.5°）时，以引擎返回的候选山向警示为准，必须复测。
- 建造年、起运年、入宅年口径不同会导出不同运盘，填写前应确认采用哪一口径。
